---
title: "Errors"
description: "Handle application errors and uncertain delivery."
---

| `code` | Meaning and next step |
| --- | --- |
| `invalid` | Unsupported or malformed fields, units, IDs or deadlines. Check the request. |
| `unauthorized` | Signature, owner/agent permissions, market scope, epoch, session or expiry does not authorize the request. Check current account authority. |
| `not-found` | An authorized lookup did not find the target in the bound account. For uncertain execution, follow [operation reconciliation](/api/methods/operation). |
| `conflict` | The ID was reused with different intent, or the read cursor belongs to a changed snapshot. Reconcile the operation or restart paging. |
| `unavailable` | Required state, freshness, risk information or external evidence is unavailable. Wait for reconciliation before dependent execution. |

Application errors arrive inside the encrypted reply as `{ kind: 'error', code }`. They are not method-specific public HTTP error responses.

The SDK throws a redacted delivery or verification error when it cannot establish a valid reply. This does not prove that the requested action was rejected: it may already be recorded or externally exposed.

Keep the original ID, reconnect and [look up the operation](/api/methods/operation). If the outcome remains uncertain, retain it for operator reconciliation rather than submit a new trade.

For a paging conflict, start again without a cursor. For a closed subscription, reconnect with fresh attestation and current authority, then obtain a new snapshot.

---
title: "Limits and reconnect"
description: "Session capacity, request bounds and reconnect behavior."
---

| Limit | Scope and value |
| --- | --- |
| Attested sessions | 8 per relay service instance, shared across accounts; pending handshakes count. |
| Enclave ingress connections | 8 per private service listener. This is separate from an account's permissions. |
| Upgraded WebSocket connections | 8 per relay instance, shared across accounts. |
| Session lifetime | At most 120 seconds per session. |
| Authenticated records | 128 per direction per session, including confirmation, reply chunks and updates. |
| Handshake, command, first subscription response and partial-frame delivery | 5 seconds per delivery operation. |
| Concurrent SDK commands | 1 per client channel; serialize requests. |
| Subscriptions and consumers | 1 subscription per channel and 1 iterator consumer. |
| Read page | 1–64 rows per request. |
| Signed application request | At most 1 KiB before encryption. |
| Application reply | At most 1 MiB before encryption, carried in bounded chunks. |
| Subscription consumer queue | 32 complete updates or 1 MiB, whichever is reached first. |
| Subscription authorization recheck | Every 500 ms. |
| Retained journal | 4,096 records or 64 MiB per journal. Exhaustion stops dependent work rather than silently deleting history. |

Eight sessions is **not** an eight-session allowance for each customer or a guaranteed limit for an entire multi-instance deployment. Shared service capacity can be reached by other accounts.

The record budget is not a trade count: handshake confirmation, large replies and updates also consume records. Reconnect with fresh attestation before a channel expires or exhausts its record budget.

On subscription closure or overflow, establish a new channel and start a read without a cursor to obtain a fresh snapshot. Delivery failure does not automatically retry an order or payout. See [lifecycle](/api/lifecycle).

These bounds are separate from venue rate limits and the risk policy's financial limits. Account authentication and agent-grant durations can impose tighter expiry.
